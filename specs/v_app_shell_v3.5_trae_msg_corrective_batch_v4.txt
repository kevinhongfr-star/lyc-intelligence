## WHAT TO FIX

### Fix 1: Chat streaming (P1 — UX blocker for production feel)

Current state: `/api/nexus-chat` returns a single JSON response after full completion. User waits with no feedback.

Required: Convert to SSE streaming — words arrive progressively like ChatGPT.

**Implementation:**
- `/api/nexus-chat` should call DeepSeek with `stream: true`
- Stream back to client using Server-Sent Events (`text/event-stream` content type)
- Frontend (`sendNexusMessage` in `nexusChat.ts`) must handle streaming response
- `ChatPageV3.tsx` must progressively append to the message as tokens arrive
- `_engine` state (lane, lensSignals, trustStage, gateFailures) should be sent as a final event at the end of the stream (after the full text), not in the initial response

**DeepSeek streaming API:**
- Use `stream: true` in the request body
- Response is `text/event-stream` with `data: { ... }` lines
- Each chunk has `choices[0].delta.content` (partial text)
- Final chunk has `choices[0].finish_reason` and `choices[0].message` with full content
- Parse with standard SSE / line-by-line reading

**Engine state injection order:**
1. Stream the text content (token by token) → user sees response building
2. After streaming completes, run `validate12Gates()` on the full text
3. Send final SSE event: `_engine` object with lane, lensSignals, trustStage, openingVector, gateFailures
4. Client persists `_engine` to `nexus_conversations` / local state

**Quality gates in streaming mode:**
- G12 voice validation still runs on the FULL response at the end (can't gate partial text meaningfully)
- If gate failures exist, log them but still show the text (auto-cleaned where possible — hedges, warm signoffs, exclamation marks, jargon, confrontational language, coach-templates already stripped by regex)
- The `validate12Gates` function already auto-cleans (replaces/strips), so use the cleaned version for streaming

**Acceptance:**
- Chat response streams word-by-word, not waiting for full completion
- User sees response building progressively (minimal perceived latency)
- Engine state (lane, trust stage, lens signals) arrives at the end of the stream
- No visual flicker or message replacement
- DeepSeek API error handling still works (stream error → show error state)

### Fix 2: Vercel function configuration (P1 — reliability)

Current state: `api/nexus-chat.ts` is NOT in `vercel.json` `functions` config. Default timeout is 10s, default memory is 1024MB.

DeepSeek streaming responses for longer answers could exceed 10s. Add explicit config:

```json
{
  "functions": {
    "api/nexus-chat.ts": {
      "memory": 1024,
      "maxDuration": 30
    }
  }
}
```

30s gives headroom for longer diagnostic responses on slow connections.

### Fix 3: Prompt file bundling assurance (P0 — belt & suspenders)

Current state: `getMasterPrompt()` reads from `nexus-engine/nexus_llm_system_prompt_v2.7.txt` via `process.cwd()`. This works on Vercel (confirmed in production test), but add a colocated copy as a failsafe so the function never has an empty prompt.

**Action:**
- Copy `nexus-engine/nexus_llm_system_prompt_v2.7.txt` → `api/nexus_llm_system_prompt_v2.7.txt`
- The fallback path in `getMasterPrompt()` already checks `api/nexus_llm_system_prompt_v2.7.txt`, so just putting the file there adds redundancy
- Both copies should always be identical (same source of truth)
