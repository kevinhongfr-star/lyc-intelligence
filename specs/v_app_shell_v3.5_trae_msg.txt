## 3-LANE FRAMEWORK (KEY v1.5 CONCEPT)

NEXUS serves three lanes. Core worldview is universal. Lane depth activates based on user context.

- **Lane 1 — Leadership Advisory:** Board-level, organizational, cross-border leadership
- **Lane 2 — Career Architecture:** Executive career transitions, positioning, advancement
- **Lane 3 — Search Operations:** Talent evaluation, selection science, search execution

**Lane detection rule (critical):** Infer lane from the user's first message. If ambiguous, start universal and let the conversation reveal the lane. **Never ask "which lane are you in?"**

China is the deepest evidence base, not the default frame. Lane-specific depth activates by detection.

The engine handles this automatically — do NOT implement lane selection UI.

### Chat (most complex — read carefully)

**Do NOT wire chat directly to an LLM API. Chat must go through the full NEXUS Engine pipeline.**

Build API routes that call the NEXUS Python engine:
- `POST /api/nexus/chat` — send a message, stream back NEXUS response
- The engine assembles the FULL 6-layer prompt stack at runtime (L0 Constitution → L1 Core → L2 Quality → L3 Patterns → L4 Scenario/Lane → L5 Turn Engine)
- 3 vertical layers feed into the stack: User Intelligence → Lens Intelligence → Recommendation Engine
- Lane detection happens on first message — automatic, no UI selector
- Pattern retrieval from 164-pattern library based on user input + context
- After each turn, lens scores update via Lens Intelligence Engine
- Quality gates are enforced by L2

**Supabase side:**
- Conversation list from Supabase conversations table (user-scoped via RLS)
- Messages saved to Supabase messages table for persistence
- User intelligence data (profile memory, milestones, artifacts) feeds U0 vertical layer

**What to preserve from the engine — do NOT simplify:**
- The full 6-layer horizontal + 3 vertical architecture
- Layer 0 Persona Constitution (always active, above everything)
- Lane detection and lane-activated depth
- Pattern retrieval from 164-pattern library
- Lens intelligence / scoring after each turn
- Recommendation engine integration
- Quality gate system

### Lenses

- Lens scores computed by Lens Intelligence Engine (L0 vertical layer)
- 11 lenses across 2 suites — definitions and scores from engine
- Tier gating from Supabase subscription tier
- Insight text generated by engine, not hardcoded
- Active/locked state from real tier + real data availability
- Lens identification system maps patterns → lens signals → scores

### Milestones

- Milestones data model in Supabase
- Also feeds the User Intelligence (U0) vertical layer of the engine

### Profile & Settings

### Booking

- Session types mapped to real session products
- Calendar + time slots = real availability
- Confirm bar = creates real booking record

## NEXUS ENGINE INTEGRATION NOTES

The Python engine code is in `nexus-engine/`. Key files and concepts:

**Prompt architecture v2.1:**
- Layer 0: Persona Master Constitution (new in v1.5 — worldview, lanes, canon, blind spots, boundaries, gravitas)
- Layer 1: Core Identity (lane-activated, 5 persona modes)
- Layer 2: Quality System (12-gate quality framework)
- Layer 3: Pattern Context (retrieved from 164-pattern library)
- Layer 4: Scenario Control / Lane Detection
- Layer 5: Turn Engine (per-turn response orchestration)

**Vertical intelligence layers:**
- U0: User Intelligence — profile, memory, milestones, artifacts
- L0: Lens Intelligence — pattern-to-lens mapping, signal scoring, 11-lens model
- R1: Recommendation Engine — trust-aligned recommendations, not pushy

**Key Python files:**
- `nexus_llm_engine.py` — NexusLLMEngine, DeepSeek client, runtime prompt assembly
- `nexus_engine.py` — PatternRetriever, ScenarioRouter
- `nexus_lens_memory_engine.py` — LensMemoryEngine, 11-lens scoring

**Deployment approach:**
- Options: (a) Python subprocess per request, (b) Vercel Function running Python, (c) separate microservice
- Choose the approach that works best with Vercel deployment
- Streaming is required — chat responses must stream token-by-token
- DEEPSEEK_API_KEY from environment variables (server-side only, never expose to client)

**Pattern library:**
- 164 patterns consolidated v3.1 (nexus_pattern_library_consolidated_v3.1.md)
- Also available as JSON for programmatic use (patterns_v1.0.json — expand/upgrade as needed)
- Patterns are the intellectual canon — they stay in the engine, never in Supabase
