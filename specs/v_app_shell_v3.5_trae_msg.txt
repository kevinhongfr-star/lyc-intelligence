## 🔴 MOST IMPORTANT RULE — READ THIS FIRST

**This is NOT a static mock build. This is NOT a simple UI skin on existing Supabase tables.**

This is a FUNCTIONAL rebuild with TWO backend layers you must wire together:

**Layer 1 — NEXUS Engine (the brain):**
- Python engine in nexus-engine/ directory
- Handles all chat intelligence: 5-layer prompt stack, pattern retrieval, scenario routing, lens scoring, memory
- Uses DeepSeek API (DEEPSEEK_API_KEY env var)
- Pattern knowledge base (JSON) and system prompts live here — NOT in Supabase
- Communicates via API endpoints you will build (Next.js route handlers that call the Python engine)

**Layer 2 — Supabase (per-user state):**
- Auth, conversations, messages, user profile, settings, documents, bookings
- User-scoped with RLS (users only see their own data)
- Same Supabase instance as DEX products — strict RLS separation between products

**Your job:** Build the v3.5 UI and wire it so that:
1. Chat messages go through the NEXUS Engine (Python), not a simple Supabase/OpenAI passthrough
2. Lens scores come from the NEXUS Lens Memory Engine, not hardcoded values
3. User-specific state (conversations, profile, settings, docs, bookings) still lives in Supabase
4. Pattern knowledge and prompt logic NEVER enters Supabase tables — it stays in the Python engine

**Mock data is allowed ONLY as a temporary scaffold during development. It must be removed before the PR.**
**PR with hardcoded mock data = rejected.**
**PR that bypasses the NEXUS Engine and wires chat directly to LLM = rejected.**

**Before writing any component, explore:**
- The existing Next.js app structure, auth flow, and Supabase schema
- nexus-engine/ — read nexus_llm_engine.py, nexus_engine.py, nexus_lens_memory_engine.py
- The system prompts in nexus-engine/system_prompts/ — understand the 5-layer stack
- patterns_v1.0.json — understand the pattern data structure

Then build on top of both foundations.

## BACKEND INTEGRATION — PER VIEW

### Chat (most complex — read carefully)

**Do NOT wire chat directly to an LLM API. Chat must go through the NEXUS Engine.**

Build API routes that call the NEXUS Python engine:
- `POST /api/nexus/chat` — send a message, stream back NEXUS response
- The engine assembles the full 5-layer prompt stack (core identity → quality system → retrieved patterns → scenario controller → turn engine)
- Pattern retrieval happens automatically based on user input + conversation context
- Scenario routing classifies the conversation type
- After each turn, the lens memory engine updates lens scores

**Supabase side:**
- Conversation list from Supabase conversations table (user-scoped via RLS)
- Messages saved to Supabase messages table for persistence
- First message in a conversation triggers scenario classification by the engine

**What to preserve from the engine:**
- The 5-layer prompt architecture — do NOT flatten or simplify
- Pattern retrieval from pattern_db/patterns_v1.0.json
- Scenario routing logic
- Lens memory / scoring updates after each turn
- Quality gate checks

### Lenses

- 11 lenses across 2 suites — definitions from engine, scores from engine based on conversation history
- Tier gating from Supabase subscription tier
- Insight text generated by engine, not hardcoded
- Active/locked state from real tier + real data availability

### Milestones

- Use existing milestones/goals data model in Supabase
- Status, progress, target dates = real data
- Click through to existing milestone detail if applicable

### Profile & Settings

- Profile from users table (name, email, company, role, tier, etc.)

### Documents

- Document list from real documents/reports table in Supabase

## NEXUS ENGINE INTEGRATION NOTES

The Python engine is in `nexus-engine/`. Key integration points:

**nexus_llm_engine.py — NexusLLMEngine class:**
- Takes DEEPSEEK_API_KEY env var
- `chat(user_message, conversation_history, scenario_id, persona)` — full turn
- 5-layer prompt assembly at runtime (not a single static system prompt)
- Pattern retrieval is part of the pipeline

**nexus_engine.py — PatternRetriever + ScenarioRouter:**
- Keyword-based pattern retrieval from patterns_v1.0.json
- Scenario classification

**nexus_lens_memory_engine.py — LensMemoryEngine:**
- Tracks 11 lens scores per user
- Updates scores based on conversation content
- Generates lens insights

**How to call from Next.js:**
- Options: (a) Python subprocess per request, (b) Vercel Function running Python, (c) separate microservice
- Choose the approach that works best with Vercel deployment
- Streaming is required — chat responses must stream token-by-token, not return full response at once
- DEEPSEEK_API_KEY comes from environment variables (server-side only, never expose to client)
